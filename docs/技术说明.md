# 技术说明

记录几个不那么显然的实现要点，尤其是「为什么热键在游戏里能生效」这件事。

## 1. 架构

```
WinForms 主窗口 (无边框、TopMost)
 ├─ Panel 工具栏（26px，图标按钮）
 ├─ Label 状态条（16px）
 └─ WebView2 控件（Dock=Fill）
       └─ 系统已安装的 Edge WebView2 运行时（不打包内核）
```

单文件 `src/Program.cs`，约 1400 行，不依赖第三方库（WebView2 SDK 除外）。

## 2. 窗口缩放：为什么需要 4px Padding

WebView2 是**子窗口**，铺满客户区后，鼠标落在它上面时 `WM_NCHITTEST` 根本不会送到主窗体——于是「拖边框缩放」失效。

解决办法：给 Form 设置 `Padding = new Padding(4)`，让 WebView2 内缩 4px，四周留出属于主窗体的空边；再在 `WndProc` 里处理 `WM_NCHITTEST`，按落点返回 `HTLEFT/HTRIGHT/HTTOP/...`。

## 3. 全局热键：两条通道

| 通道 | 何时失效 |
|---|---|
| `RegisterHotKey` | 前台是高完整性级别（管理员）窗口时 **收不到** |
| `SetWindowsHookEx(WH_KEYBOARD_LL)` | 同上（UIPI 限制），但普通场景更稳 |

两条同时注册，任一命中就触发，用 250 ms 时间戳去抖，避免一次按键触发两次。

钩子回调里**只做三件事**：比对 vk、比对修饰键（`GetAsyncKeyState`）、`PostMessage` 给自己的窗口。绝不在钩子里做耗时操作，否则超过系统 300 ms 阈值会被静默卸载钩子。日志也只在内存队列里排一行，由 UI 定时器统一写盘。

```csharp
if (kb.vkCode == b.Vk && ModifiersMatch(b.Mods)) {
    if (unchecked(now - b.LastTick) > 250) { b.LastTick = now; PostMessage(Handle, WM_APP_ACTION, (IntPtr)b.Action, ...); }
    return (IntPtr)1;   // 吞掉按键
}
```

修饰键策略：绑定的是**单键**时不做修饰键比对（游戏里常按着 `Shift` 冲刺，多按一个修饰键不该让热键失效）；绑定的是组合键时要求完全一致。

## 3.1 单键热键为什么不能走 RegisterHotKey

`RegisterHotKey(hwnd, id, 0, VK_5)` 成功之后，按 `5` 会在**系统层**被吃掉——钩子也拦不回来，于是任何程序里都打不出 `5`。

所以开启「智能放行」时，单键热键**跳过** `RegisterHotKey`，完全由低级键盘钩子处理：钩子里先判断当前场合该不该吃键，不该吃就 `CallNextHookEx` 原样放行。组合键仍走 `RegisterHotKey`（组合键不影响正常打字）。

## 3.2 场合判断（SmartPass）

判定只做几个轻量 Win32 调用，不吃 CPU、也不依赖辅助功能树：

```csharp
if (!cfg.SmartPass) return true;                       // 老行为：任何地方都吃键
IntPtr fg = GetForegroundWindow();
if (fg == Handle) return true;                          // ① 自己的窗口
uint pid; GetWindowThreadProcessId(fg, out pid);
if (cfg.HotkeyApps.Contains(ExeNameOf(pid))) return true;  // ③ 白名单（窗口化游戏）
return IsFullScreenWindow(fg);                          // ② 全屏（GetWindowRect ⊇ 显示器 rcMonitor）
```

> 一开始试过用 UIA 判断「焦点是不是在输入框」，实测不可靠：WinForms 输入框的 `ControlType` 报成 `Pane`（只有类名里带 `EDIT`），真 Chrome/Edge 的焦点报成 `Document`。全屏 + 白名单这套规则虽然朴素，但可预测、不会误伤打字。

## 4. 为什么必须提权（UIPI）

Windows 的 **User Interface Privilege Isolation**：前台窗口完整性级别高于本进程时，本进程收不到该窗口相关的输入通知，全局热键与低级钩子都不会回调。

游戏（如原神）由启动器以管理员权限启动 → 想在其前台时收键，本程序也必须提权。
程序启动时检查 `WindowsPrincipal.IsInRole(Administrator)`，未提权且配置允许时用 `ProcessStartInfo { Verb = "runas" }` 自提权重启；用户拒绝则以普通权限继续（仅热键失效）。

## 5. 页面操作全部走 JS

- **暂停**：找到 `readyState > 0` 的第一个 `<video>`，`paused ? play() : pause()`
- **快进/快退**：`video.currentTime += delta`，并夹在 `[0, duration - 0.2]`，避免跳到末尾直接结束
- **缩放**：`document.documentElement.style.zoom = 1.1`
- **Ctrl+滚轮缩放**：注入脚本监听 `wheel`（`passive:false` + `preventDefault`），把方向用 `window.chrome.webview.postMessage` 回传宿主

`ExecuteScriptAsync` 返回的是 JSON 字符串（要 `Trim('"')`），据此更新状态条文字。

## 6. 下载拦截

有些站点（含反爬策略）会把本该渲染的 HTML 以附件形式下发，Chromium 于是把它存成 `下载.htm`。

处理：`CoreWebView2.DownloadStarting` 里 `e.Cancel = true`，若该 URL 是 http(s) 且未重试过，延迟 200 ms 后改用 `Navigate()` 正常打开；用 `HashSet<string>` 防死循环。

## 7. 单实例与配置

- 单实例：`new Mutex(true, "PinPeek.SingleInstance.v1", out created)`，重复启动弹提示后退出——避免两个实例抢同一个热键。取锁带重试（30 × 200 ms），这样「以管理员身份重启」时新进程不会因为旧进程还没松锁而误报“已经在运行”
- 配置：exe 同目录的 `pinpeek.ini`，退出时写回；删除该文件即恢复默认
- `[bookmark]` 默认项只在配置文件里没有收藏时补一次，避免每次启动翻倍
- 新增 `smartpass=`（智能放行开关）与 `hotkeyapps=`（热键白名单，逗号分隔小写 exe）

## 8. 退出流程：关窗口必须退干净

早期版本点系统 `✕` 会 `e.Cancel = true; Hide()` 收进托盘，进程一直挂在后台（任务管理器里能看到 3~4 MB 的 PinPeek）。现在：

1. 任何来源的关闭（工具栏 `✕`、`Alt+F4`、任务栏右键关闭、关机）都进同一个 `RealExit()`；
2. 先 `DisposeResources()`：卸键盘钩子、注销全局热键、销毁托盘图标、`WebView2.Dispose()`；
3. 起一个 3 秒的**看门狗线程**，超时直接 `Environment.Exit(0)`（WebView2 偶尔会卡在关闭上）；
4. 主线程再补一次 `Environment.Exit(0)`，`Application.Run` 返回后还有一道兜底。

实测：点 `✕` 后主进程与 `msedgewebview2.exe` 子进程全部消失。

## 9. 调试技巧

运行目录放一个 `debug.flag` 文件，程序会给 WebView2 附加 `--remote-debugging-port=9222`，之后可以用 Chrome DevTools Protocol 直接驱动页面做自动化验证（点击、读 `video.currentTime`、监听下载事件），这是验证「点击/跳转/播放」逻辑最省事的方式。

热键相关的诊断日志固定写在 `%LOCALAPPDATA%\PinPeek\hotkey.log`（`HOTKEY ... registerOk=`、`HOOK installed=`、`HOOK TRIGGER`），排查「热键没反应」先看这个文件。
